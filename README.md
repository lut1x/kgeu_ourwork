# Tech Monitor / SCADA

Учебная система: React → nginx → Node.js → MySQL 8.4. Локальный стенд использует симулятор и Mailpit.

## Raspberry Pi / ESP32 через Интернет

Раздел администратора «Платы и устройства» управляет отдельными шлюзами, обнаруженными ESP32 и привязками каналов. [Установка на Raspberry](docs/raspberry-deploy.md), исходники и пример UART-протокола — в `raspberry-gateway/`. Новый API `/api/collector/v1/` использует отдельный ключ платы, сохраняет время измерения и исключает дубликаты. Старый `/api/data` продолжает работать для симулятора и прежних клиентов.

## Локальный запуск

Нужен Docker Desktop с Linux containers. В `.env.local` хранятся ключ шифрования `ACCOUNT_ENCRYPTION_KEY` и ключ приема телеметрии `INGEST_API_KEY` (по 64 hex-символа). Только для новой установки сгенерируйте их в PowerShell:

```powershell
$taskRng = [System.Security.Cryptography.RandomNumberGenerator]::Create()
foreach ($taskName in @('ACCOUNT_ENCRYPTION_KEY', 'INGEST_API_KEY')) {
  $taskKey = New-Object byte[] 32
  $taskRng.GetBytes($taskKey)
  ($taskName + '=' + ([BitConverter]::ToString($taskKey).Replace('-', '').ToLower())) | Add-Content .env.local
}
$taskRng.Dispose()
```

Генерируйте ключ только для новой базы. В текущем проекте он уже создан. Повторная генерация сделает существующие зашифрованные данные недоступными.

```sh
docker compose --env-file .env.local -f docker-compose.yml -f docker-compose.dev.yml up --build -d
```

* Приложение: http://localhost
* Локальная почта: http://localhost:8025

Регистрация создаёт учётную запись и сессию сразу, без отправки писем. Mailpit перехватывает письма сброса пароля в локальном контуре; на реальные адреса они не уходят.

При обновлении backend автоматически создает новые таблицы и шифрует существующие профили. Старые учетные записи продолжают работать, но не помечаются как подтвержденные. Их scrypt-хеши обновляются до Argon2id при следующем успешном входе. Новые требования пароля применяются к регистрации, созданию администратора и сбросу. Старые пароли автоматически не заменяются.

MySQL использует отдельный volume `mysql8_data`; старый volume MariaDB не удаляется и автоматически не импортируется.

## Роли и права

Права дополнительно ограничиваются группами датчиков. Администратор назначает оператору или технологу одну или несколько групп в разделе «Датчики и группы» → «Доступ пользователей». Внутри группы можно выбрать отдельные скрытые датчики. Без групп новый пользователь не получает доступ к телеметрии. Существующим пользователям при миграции сохраняется доступ к первоначальному контуру охлаждения.

Группы, названия, типы, единицы измерения, подключение и отключение датчиков меняет только администратор. Технолог может менять диапазон и пороги только у доступных ему датчиков. Отзыв группы или скрытие исключает канал из каталога, текущих значений, трендов, истории, статистики, CSV/SQL-экспорта и WebSocket. Скрытие действует для конкретного пользователя; отключение датчика администратором действует глобально. При переносе датчика в другую группу доступ пересчитывается по новой группе.

| Возможность | Оператор | Технолог | Администратор |
|---|---|---|---|
| Мониторинг, текущая телеметрия, тренды, профиль | Да | Да | Да |
| Журнал исторических данных | Нет | Да | Да |
| Скачать CSV и SQL с показаниями | Нет | Да | Да |
| Настроить пороги доступных датчиков | Нет | Да | Да |
| Управлять учетными записями и сбросом паролей | Нет | Нет | Да |

Права проверяются сервером, а не только видимостью кнопок. SQL-экспорт содержит таблицу показаний, без учетных записей, хешей, сессий и ключей. Регистрация всегда создает оператора.

## Регистрация

При регистрации проверяются формат адреса, заполнение имени и фамилии, требования к паролю и совпадение паролей. Учётная запись оператора и сессия создаются сразу. Проверки MX/DNS и подтверждения кодом нет; доступность SMTP не влияет на регистрацию. Поле `email_verified` остаётся ложным: владение ящиком не проверялось.

Почтовые коды используются только для сброса пароля. Старые маршруты `/api/auth/verify-email` и `/api/auth/resend-email` удалены.

## Сброс пароля

В панели администратора нажмите «Сбросить пароль». Подтвердите действие вводом почты целевого пользователя и своего текущего пароля. Пользователю придет письмо с кодом и ссылкой на форму установки нового пароля. До подтверждения старый пароль действует. После подтверждения прежние сессии и WebSocket-соединения завершаются. Запрос и завершение сброса записываются в `account_audit` без секретов.

Требования к новому паролю: 12–128 символов, заглавная и строчная буквы, цифра и спецсимвол, без пробелов. Проверка есть на frontend и backend. Пароли никогда не возвращаются администратору.

## Защита учетных записей

* Пароли: Argon2id, 64 MiB памяти, три прохода, параллелизм 1 и индивидуальные соли.
* Почта, имя, фамилия: AES-256-GCM с отдельным случайным IV и проверкой целостности.
* Поиск и уникальность почты: HMAC-SHA-256 индекс с отдельным ключом, полученным через HKDF.
* ID и роль остаются служебными полями для связей и проверки прав.
* Сессии: случайные токены в HttpOnly/SameSite=Strict cookie, только SHA-256 токенов в БД, срок семь дней.

Ключ хранится вне БД в игнорируемом Git файле `.env.local`. Сохраняйте его отдельную защищенную резервную копию. На сервере используйте хранилище секретов. Шифрование защищает содержимое дампа БД; оно не защищает от полного захвата backend с доступом к ключу. HTTPS необходим для защиты передаваемых данных. Не называйте один алгоритм «самым лучшим»: защита зависит и от ключей, транспорта и прав доступа.

Подходы основаны на [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) и [OWASP Cryptographic Storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html).

## SMTP на сервере

Для выбранного Gmail готова локальная настройка: [инструкция](docs/gmail-setup.md), команда `powershell -ExecutionPolicy Bypass -File .\scripts\Configure-Gmail.ps1`. Нужны адрес Gmail и пароль приложения. До их ввода продолжает использоваться Mailpit.

Не используйте dev-конфигурацию Mailpit на внешнем сервере. Задайте в защищенном env-файле:

```dotenv
ACCOUNT_ENCRYPTION_KEY=<существующий ключ при переносе базы>
APP_URL=https://your-host.example
COOKIE_SECURE=true
MAIL_MODE=smtp
SMTP_HOST=smtp.your-provider.example
SMTP_PORT=587
SMTP_USER=<логин сервиса>
SMTP_PASSWORD=<пароль приложения>
MAIL_FROM=Tech Monitor <noreply@your-domain.example>
```

Для порта 465 включается TLS сразу, для остальных SMTP-портов требуется STARTTLS с проверкой сертификата. Настройте HTTPS на внешнем nginx, собственные секреты БД и ограничение доступа к `POST /api/data` сетью датчиков. Этот маршрут предназначен для симулятора/UART и пока не использует пользовательскую сессию.

## Первый администратор

В текущем локальном стенде администратор уже существует; данные входа сохранены в `.env.local`. Для новой базы после запуска backend:

```powershell
$env:ADMIN_EMAIL = 'admin@your-domain.example'
$taskPassword = Read-Host 'Пароль администратора' -AsSecureString
$env:ADMIN_PASSWORD = [System.Net.NetworkCredential]::new('', $taskPassword).Password
docker compose --env-file .env.local exec -e ADMIN_EMAIL -e ADMIN_PASSWORD backend node create-admin.js
Remove-Item Env:ADMIN_PASSWORD
```

## Подключение нескольких датчиков

Администратор создает группу и добавляет датчик в разделе «Датчики и группы». Для нового датчика показывается уникальный токен; сервер хранит только его SHA-256 хеш. Ключ канала (`sensor_key`) остается стабильным при переименовании. Устройство передает:

```http
POST /api/data
Content-Type: application/json
X-Sensor-Token: <токен датчика>

{"sensor_key":"temperature_07","value":42.5}
```

Неверный токен получает 401. Датчик с выключенным состоянием не принимает показания. Администратор может перевыпустить токен, после чего старый прекращает действовать. Только администратор подключает новые каналы; API не создает датчики из входящих пакетов автоматически.

Локальный симулятор передает шесть каналов в двух группах. Для доверенного многоканального коллектора есть отдельный `INGEST_API_KEY` в `.env.local`; это секрет с доступом ко всем каналам. Коллектор отправляет `X-Ingest-Key` и JSON `{"readings":[{"sensor_key":"temp_01","value":55}]}`. Этот ключ не выдается пользователям приложения. Все HTTP, WebSocket, экспорт и журналы фильтруются по доступу пользователя.

UART-мост передает только фактическую температуру, без фиктивных нулевых каналов. Для отдельного устройства задайте `SERIAL_PATH`, `SENSOR_KEY` и `SENSOR_TOKEN`. Несколько независимых последовательных устройств можно подключить отдельными экземплярами моста с собственными путями и ключами. Текущий бинарный протокол разбирает один температурный канал на экземпляр; мультиплексирование адресов одного UART требует спецификации оборудования.

Старые показания сохранены в таблице `readings` и при первой миграции скопированы в `sensor_samples`. Повторный запуск их не дублирует. Все новые показания записываются в `sensor_samples` с `sensor_id`.
