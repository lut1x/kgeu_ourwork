# DietPi и VPS: выполненная настройка 16 октября 2026

## Установлено

- Raspberry Pi 2 Model B Rev 1.1, ARMv7, DietPi 10.7 / Debian 13.
- Локальный адрес при проверке: `192.168.3.32`, Ethernet, DHCP. Адрес не закреплялся вручную; при необходимости зарезервировать его в роутере по MAC `b8:27:eb:0a:72:8d`.
- SSH root по отдельному ключу: `.server-access/raspberry-deploy`, отпечаток сервера закреплён в `.server-access/pi_known_hosts`. Закрытый ключ не публиковать.
- Python 3.13.5, pyserial, SQLite, CA-сертификаты, D-Bus и SFTP.
- Шлюз 1.0.1 в `/opt/scada-gateway/gateway.py`; служба `scada-gateway.service` включена и работает от отдельного пользователя `scada-gateway` с доступом `dialout`.
- Ключ отдельной платы зарегистрирован на VPS, collector ID **2**, имя **Raspberry Pi 2 DietPi (192.168.3.32)**. Ключ хранится в root-only `/etc/scada-gateway/gateway.env`; защищённая копия на VPS — `/root/scada-collectors/pi2-dietpi.env`.
- URL сервера: `https://scada.lut1x1337.ru:9443`. VPS: `147.45.238.163`, проект `/opt/tech-scada`, команда управления `/usr/local/bin/scada`.

## Восстановление

- При завершении процесса шлюза systemd перезапускает его через 5 секунд; зависание основного цикла обнаруживается через 90 секунд. Сбой потока управления UART завершает процесс для перезапуска.
- Ограничения шлюза: 128 MiB памяти, 96 задач; журнал в RAM ограничен 16 MiB.
- Аппаратный watchdog Raspberry активен, timeout 15 секунд; обслуживается systemd. Проверено состояние устройства, аппаратное зависание всей ОС намеренно не вызывалось.
- NTP работает постоянно: DietPi `CONFIG_NTP_MODE=4`. Часовой пояс `Europe/Moscow`; временные метки телеметрии передаются в UTC.
- В `/boot/firmware/config.txt` включены UART и watchdog. Из `/boot/firmware/cmdline.txt` удалена последовательная консоль; локальная консоль `tty1` сохранена. Последовательные getty отключены. GPIO UART — `/dev/serial0` → `/dev/ttyAMA0`.
- Существующий DHCP-клиент обслуживает Ethernet. Потеря Интернета не вызывает циклические перезагрузки; шлюз сохраняет назначенные каналы в SQLite и повторяет отправку.
- На VPS Docker и контейнеры имеют автозапуск. `scada-stack.service` поднимает MySQL, backend и frontend при загрузке хоста.
- `scada-recover.timer` проверяет локальный MySQL, API и HTTPS раз в минуту; после трёх неудачных проверок перезапускает соответствующий сервис. Повторные перезапуски ограничены одним за пять минут для каждого сервиса. Внешний DNS/Интернет в диагностике не участвует. Для обслуживания создать `/etc/scada-maintenance`, затем удалить его, чтобы вернуть восстановление.
- После настройки по запросу пользователя симулятор удалён с VPS: контейнер, образ, исходники и сервис в серверных Compose-файлах. Удалены шесть демонстрационных датчиков, 766974 показания `sensor_samples`, 3942 старые записи `readings` и две пустые демонстрационные группы. Перед удалением сделан бэкап. Шлюз Raspberry и его ключ сохранены; VPS принимает и хранит данные платы.

## Резервные копии

- Raspberry: `scada-gateway-backup.timer`, ежедневно около 03:15 МСК; семь согласованных SQLite-снимков вместе с ключом, кешем конфигурации и исходником в `/var/backups/scada-gateway/`, только для root. Используется SQLite Backup API, учитывающий WAL.
- Исходные настройки загрузки и DietPi сохранены в `/root/scada-setup-backups/`.
- Начальный архив установленного шлюза скачан на управляющий компьютер в `.server-access/pi2-installed-backup.tar.gz`. Архив содержит секрет доступа платы, не публиковать.
- VPS: существующий `scada-backup.timer` ежедневно в 06:30 МСК сохраняет MySQL и ключи приложения в `/var/backups/tech-scada/`; новая копия создана вручную после настройки. Настроено автоматическое обновление TLS-сертификата и reload nginx после обновления.
- Ежедневные копии остаются на устройствах, с которых сняты. Автоматическое внешнее хранилище бэкапов не подключалось.

## Проверено на установленной системе

1. Все три Python-теста прошли на физической Raspberry, включая Linux pseudo-UART, фрагментацию сообщений, повторное открытие SQLite и подтверждение доставки.
2. Сквозной тест на Raspberry: pseudo-UART → SQLite → HTTPS с проверкой сертификата → реальная MySQL на VPS. Тестовые 12 мА преобразованы в 5 бар для диапазона 0–10 бар. Проверены сохранение при недоступном endpoint, исходное время и повторная доставка без дубликатов. Использовались отдельные временные collector/group/sensor, все тестовые сущности и показания удалены.
3. Процесс установленного шлюза намеренно заморожен SIGSTOP: systemd обнаружил watchdog timeout и автоматически запустил новый процесс.
4. API SCADA на VPS намеренно заморожен SIGSTOP: контроль состояния обнаружил три неудачные проверки, перезапустил backend, HTTPS API вернулся в `status: ok`.
5. Raspberry штатно перезагружена; boot ID изменился. Ethernet сохранил адрес, SSH и шлюз запустились автоматически, время синхронизировано, watchdog активен, SQLite `integrity_check` вернул `ok`. VPS получает heartbeat шлюза 1.0.1.
6. Обновлённый установочный архив опубликован на VPS. SHA-256 скачанного HTTPS-архива совпал с серверным файлом.

## Оставшаяся аппаратная проверка

Пользователь подтвердил, что ESP32 пока не подключён. Настоящий аналоговый вход, калибровка 4–20 мА, физические USB/GPIO-линии и прошивка ESP32 ещё не проверялись. Шлюз ожидает строки `scada-uart-v1`, пример и вспомогательный заголовок — в `raspberry-gateway/README.md` и `esp32_scada.h`. Rock Pi на физическом оборудовании не проверялся.

В журнале и `vcgencmd get_throttled` обнаружены **текущие и прошлые просадки питания** (`0x50005`). Нужен исправный блок питания и качественный короткий micro-USB кабель. Программное восстановление не устраняет нестабильное питание и не гарантирует сохранность SD-карты при внезапном обрыве питания.

## Диагностика

Панель автоматически синхронизирует каталог и последние значения каждые 5 секунд, дополняя поток показаний WebSocket; после возвращения во вкладку выполняется обновление. Фоновая синхронизация не очищает графики и сохраняет более свежие значения WebSocket. Недоступные по новым правам датчики удаляются из локального состояния после синхронизации. Списки плат, датчиков и пользователей обновляются автоматически; редактируемые формы не пересоздаются на каждом опросе. Раздел, группа и поиск сохраняются в URL-фрагменте и восстанавливаются после F5. Восстановление раздела учитывает роль пользователя.

Индикатор внизу боковой панели проверяет `/api/communication-status` каждые 5 секунд. Зелёный статус возможен, только если все включённые платы присылали heartbeat менее 60 секунд назад и не сообщают ошибок. Выключенные вручную платы исключены из проверки; если выключены все, показан нейтральный статус «Все шлюзы отключены». Включённая, но ещё не подключавшаяся плата делает общий статус красным. Пустой реестр отображается отдельно; потеря связи панели с сервером и невозможность проверить статус не показываются как исправный канал. API требует входа и отдаёт только общие счётчики без имён, ключей и портов.

На странице «Платы и устройства» доступны карточки со сводкой, включение/выключение, настройка UART, замена ключа, фильтр устройств и удаление платы с подтверждением. Удаление доступно только администратору: ключ отзывается, обнаруженные устройства и привязки удаляются одной транзакцией; датчики SCADA и история измерений сохраняются. Повторное подключение удалённой платы требует новой регистрации и ключа. Проверено на временном шлюзе через API VPS, включая запрет анонимного удаления, повторное удаление (404), отзыв ключа (401) и сохранность истории. Пользовательские платы для проверки не удалялись.

На Raspberry:

```sh
systemctl status scada-gateway
journalctl -u scada-gateway -f
timedatectl
vcgencmd get_throttled
sqlite3 /var/lib/scada-gateway/queue.sqlite 'SELECT COUNT(*) FROM queue;'
systemctl start scada-gateway-backup
```

На VPS:

```sh
scada ps
systemctl status scada-stack scada-recover.timer scada-backup.timer
journalctl -u scada-recover -n 30
systemctl start scada-backup
```
